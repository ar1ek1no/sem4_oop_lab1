# План тестирования (ЛР3)

**Объект:** «Управление финансовой системой», веб-версия на Flask + SQLite, версия 0.2.0.
**Дата:** 03.11.2026. **Исполнитель:** студент 3 курса, ВПО.
**Основание:** [`SRS_finance.md`](../requirements/SRS_finance.md) — FR-1…FR-16, NFR-1…NFR-6; [`../ISSUES.md`](../requirements/ISSUES.md) — реестр дефектов.

## 1. Цель тестирования

Подтвердить, что реализация соответствует требованиям SRS, и найти расхождения:

1. проверить каждый FR положительными и отрицательными проверками;
2. проверить NFR, которые можно измерить (пароли, ошибки, логи, доступ к чужим данным, отклик);
3. собрать метрики и убедиться, что критерии завершения выполнены;
4. зафиксировать найденные дефекты и убедиться, что они исправлены.

## 2. Области тестирования

| Область | Что проверяем | Требования | Уровень |
|---|---|---|---|
| Регистрация и вход | создание только клиента, подтверждение, отказ, пароль по хэшу | FR-1, FR-2, FR-3, FR-4, NFR-2 | интеграционный, сценарный |
| Счета и вклады | открытие, закрытие, типы счетов, начисление процента | FR-5, FR-6, FR-7, FR-11 | модульный, интеграционный |
| Переводы | свои счета, блокировка, нехватка средств, сумма, тот же счёт | FR-8, FR-9, FR-14, NFR-5 | модульный, интеграционный, сценарный |
| История | откуда/куда/сколько/когда, статусы | FR-10, NFR-4 | интеграционный |
| Зарплатный проект | подача, подтверждение, отклонение, отзыв, период выплаты | FR-12, FR-13 | сценарный |
| Журнал и отмена | все действия, отмена, повторная отмена, старые записи | FR-15, NFR-4 | модульный, интеграционный |
| Доступ и безопасность | прямой URL без входа, IDOR, роли, ошибки без стека | NFR-3, NFR-5 | интеграционный |
| API | токен, коды ответов, структура, роли | FR-16 | интеграционный (Postman — ЛР4) |
| Производительность | время отклика, 20 пользователей | NFR-1, NFR-6 | нагрузочный (ЛР5) |
| Вёрстка и совместимость | адаптивность, 3 браузера, интерактив | — | UI (ЛР4) |

**Что не тестируем и почему:**

| Область | Причина |
|---|---|
| Старый слой `ui/` на tkinter | в веб-версии не используется, исключён из покрытия; гонять его — тестировать мёртвый код |
| Миграция БД на больших объёмах | выполняется один раз при старте; проверена отдельным тестом `test_migration`, нагрузка на миграцию не влияет на продукт |
| Внешние сервисы | их нет: платежи, проценты и подтверждения моделируются внутри; подделывать HTTP-заглушки нечего |
| Инфраструктура (ОС, сеть, права файлов) | вне границ приложения, проверяется администратором |
| Нагрузочное и UI-тестирование | вынесено в ЛР4 и ЛР5, чтобы не дублировать инструменты |

## 3. Тестовая стратегия

**Пирамида (снизу вверх):**

| Уровень | Кол-во тестов | Инструмент | Что проверяет |
|---|---|---|---|
| Модульное | 148 | pytest + `unittest.mock` | логика сервисов и команд без БД: проверки, ветки отказов, моки репозиториев |
| Интеграционное | 111 | pytest + SQLite | HTTP-маршруты, шаблоны, API, репозитории, миграция, обработка ошибок |
| Сценарное | 5 | pytest + HTTP | переходы состояний заявки и счёта из диаграммы (ЛР1 п. 4) |
| Системное ручное | — | браузер + Postman | проходит по чек-листу, результаты в [`TEST_RESULTS.md`](../test-results/TEST_RESULTS.md) |
| UI-автотесты | ЛР4 | Playwright + Page Object | вёрстка, интерактив, скриншоты при падении |
| Нагрузочное | ЛР5 | Locust | профиль нагрузки и точка деградации |

**Виды тестирования:** функциональное (позитивные, негативные, граничные значения), регрессионное (весь набор перед каждым коммитом), тестирование безопасности (IDOR, роли, ошибки), совместимости (ЛР4), производительности (ЛР5), исследовательское (ручной проход по чек-листу).

**Принципы:** Arrange–Act–Assert в каждом тесте; тест создаёт свои данные; тесты не зависят от порядка запуска и друг от друга (своя БД-файл на тест); моки — только на границах (репозитории, БД).

## 5. Критерии

| Критерий | Значение |
|---|---|
| **Начала** | приложение собирается, миграция БД проходит, smoke-прогон зелёный, тест-кейсы утверждены |
| **Приостановки** | падает больше 10 % тестов или найден блокирующий дефект (нельзя войти, теряются деньги) |
| **Возобновления** | дефект исправлен, регрессионный прогон зелёный |
| **Завершения** | все тест-кейсы выполнены; TSP ≥ 95 %; покрытие требований 100 %; покрытие кода ≥ 70 %; нет открытых дефектов важности «критический» и «высокий» |
| **Приёмочные** | все FR высокого приоритета покрыты тест-кейсами и пройдены; NFR-1…NFR-5 подтверждены измерениями |

## 6. Метрики (раздел 6.2 методички)

| Метрика | Формула | Целевое значение |
|---|---|---|
| Процент успешного прохождения тест-кейсов | `TSP = T_success / T_total · 100 %` | ≥ 95 % (финальная фаза — 85 %) |
| Процент выполнения тест-кейсов | `T_ex = T_executed / T_total · 100 %` | 100 % |
| Покрытие требований тест-кейсами | `R_cov = R_covered / R_total · 100 %` | 100 % |
| Плотность покрытия требований | `R_density = Σ T_i / (T_total · R_total) · 100 %` | ≥ 100 % (у каждого требования ≥ 1 кейс) |
| Покрытие кода | `C = lines_covered / lines_total` | ≥ 70 % |
| Устранение дефектов по важности | `F = F_fixed / F_total` по каждой важности | 100 % для критических и высоких |
| Плотность дефектов | `D = N_defects / N_FR` | справочно |

## 7. Риски

| Риск | Влияние | Действие |
|---|---|---|
| Тесты зависят от порядка запуска | ложные падения | отдельная БД-файл на тест, фабрики данных |
| Моки расходятся с реальным поведением | пропущенный дефект | интеграционные тесты на реальной SQLite дублируют ключевые сценарии |
| WSL без GUI | UI-тесты не запускаются | headless Chromium; при отсутствии библиотек — прогон на Windows |
| Кириллица в путях и данных | ошибки кодировки | все шаблоны в UTF-8, проверка в интеграционных тестах |
| Стереть рабочую БД тестами | потеря данных | тесты работают только во временных папках, `finance.db` не трогают |
