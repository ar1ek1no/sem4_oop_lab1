# План блоков: ООП-лаба и база для ВПО

Один проект закрывает два предмета: лабу по ООП («Управление финансовой системой») и все пять лаб по верификации ПО. Поэтому порядок блоков подчинён не только ООП, но и будущим лабам ВПО.

**Что уже есть в папке:** `app.py` на `customtkinter` (логин, роутинг по роли на `ClientFrame`/`ManagerFrame`/`AdminFrame`), `main.py` (`init_db` + запуск), `finance.db` с таблицами `users`, `banks`, `enterprises`, `employment`, `accounts`, `salary_requests`, `transaction_logs`, git с remote на GitHub.

**Ключевое решение:** слой представления переносится на **Flask + Jinja + SQLite**; доменная логика (модели, сервисы, валидация) сохраняется и структурируется по SOLID. Без веба задания 4–5 ВПО невыполнимы (Postman, Selenium/Playwright, нагрузка, проверки безопасности).

| Блок | Что делаем | Что закрывает | Куда идёт в ВПО |
|---|---|---|---|
| **1. Разведка** | что работает, чего нет по заданию, карта файлов, план | — | — |
| **2. Архитектура и README** | слои: модели → репозитории → сервисы → представление; схема компонентов; README (назначение, стек, запуск) | задание ООП: «выбор языка и технологии» | **ЛР1 п.1** (README, модули, точки интеграции) |
| **3. Домен** | модели (`User`, `Bank`, `Enterprise`, `Account`, `Deposit`, `Transaction`, `SalaryRequest`), базовый класс счёта и наследники, репозитории, сервисы, валидация, Strategy для переводов, Repository для БД | ООП + SOLID | **ЛР1 п.2** (требования), **ЛР2** (тесты) |
| **4. Flask-каркас** | фабрика приложения, маршруты, шаблоны, сессии, логин, роутинг по роли, `login_required` | авторизация и роли | **ЛР4 п.2** (API), **ЛР4 п.3** (безопасность) |
| **5. Клиент** | счета (открыть/закрыть/перевод/история), вклады (создать/закрыть/перевод/накопление), предприятия, заявка на зарплатный проект, получение зарплаты | весь функционал клиента | **ЛР3** (тест-кейсы), **ЛР2** (сценарные тесты) |
| **6. Менеджер и админ** | подтверждение регистраций, предприятия и сотрудники, заявки, блокировки; админ: журнал + **отмена действий** (Command) | функционал менеджера и админа | **ЛР1 п.4** (жизненный цикл заявки), **ЛР2** (сценарии переходов) |
| **7. Валидация и тесты** | проверки полей, юнит-тесты с моками, интеграционные на БД, сценарные цепочки, покрытие ≥ 70 % | валидация + тесты | **ЛР2** целиком |
| **8. Финал** | прогон всех функций, README, скриншоты, коммиты, `ISSUES.md` с расхождениями | сдача ООП | **ЛР1 п.3** (верификация требований) |

## Порядок и зависимости

- Блоки 1–3 дают ядро, без которого веб-слой бессмысленен.
- Блок 4 можно начать раньше, но тогда маршруты будут пустыми: лучше после 3.
- Блок 7 опирается на 3 и 5: тестировать нечего, пока нет функций.
- Блок 8 — обязательный: без README ВПО-лабы сдавать нечем, её читают вслух.

## Что важно не переусложнить

- Пять лаб ВПО требуют **работоспособности и понятности**, а не промышленной архитектуры. Достаточно: слои, интерфейсы, валидация, журнал, отмена.
- Пароли — хэшировать (в текущей базе они в открытом виде: для ВПО это же станет дефектом в `ISSUES.md`, и это отличный материал для лабы 1 п.3).
- Одна БД, один процесс, без очередей и фоновых задач.

## Заготовки для ВПО, которые делаются «по ходу»

- **Жизненный цикл:** заявка на зарплатный проект (`pending → approved → rejected`) — идеальная сущность для диаграммы состояний и сценарных тестов.
- **IDOR:** клиент открывает `/accounts/<id>` — проверка владельца станет проверкой безопасности в ЛР4.
- **Логи:** журнал действий уже есть в схеме — он же будет объектом для проверок логирования.
