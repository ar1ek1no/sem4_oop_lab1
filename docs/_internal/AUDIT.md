## 3. Дефекты и пробелы (основа для `ISSUES.md` в ВПО)

**D-1. Пароли хранятся и сравниваются в открытом виде.**
`models.py:18` — `password = Column(String)`; `auth_service.py:19` — `user.password == password`. Нарушает NFR-2. В веб-версии обязательно хэширование.

**D-2. При регистрации можно выбрать любую роль.**
`auth_service.py:8` — `register(username, password, role)`, и `login_frame` передаёт выбранную роль. Значит любой может зарегистрироваться менеджером или администратором. По заданию регистрируется **только клиент**; остальные роли создаются иначе. Это дыра безопасности, а не косметика.

**D-3. Нет проверки владельца счёта (IDOR).**
`bank_service.py:16` — `transfer_money(from_id, to_id, amount)` проверяет блокировку и баланс, но **не проверяет, что `from_id` принадлежит текущему пользователю**. Зная чужой `id`, клиент переведёт чужие деньги. Идеальный кейс для проверки безопасности в ВПО ЛР4 (подмена `id`).

**D-4. Отмена действий сделана через `if/elif` по типу операции.**
`admin_service.py:79` — 7 ветвей, а данные «упакованы» в чужие поля: `amount` хранит `enterprise_id`, `target_id` — `user_id`. Это хрупко (добавление операции требует правки нескольких мест) и нечитаемо. По ООП здесь просится паттерн **Command**: у каждого действия свой класс с `execute()` и `undo()`.

**D-5. `BankRepository` наследует ORM-модель.**
`repositories/bank_repository.py:3` — `class BankRepository(Bank)`. Репозиторий не должен быть наследником сущности: смешаны две ответственности (SRP).

**D-6. Состояние пользователя хранится в статическом поле сервиса.**
`auth_service.py:5` — `_current_user` на уровне класса. В десктопе работает, в вебе — нет: один процесс обслуживает всех пользователей, и «текущий пользователь» станет общим. При миграции заменяется на сессию Flask.

**D-7. Зарплата — заглушка.**
`bank_service.py:52` — `salary_amount = 1000.0` фиксированной строкой. Нет ни ставки, ни периода; повторное получение не ограничено.

**D-8. Тестов нет.**
Ни одного файла тестов. Для ВПО ЛР2 это первый пункт работы.

**D-9. Валидация частичная.**
Проверяются: длина логина и пароля, `amount > 0`, блокировка, достаточность средств. Не проверяются: отрицательные суммы на уровне формы, пустые обязательные поля, ввод не-чисел, совпадение счетов отправителя и получателя (`from_id == to_id` можно перевести самому себе — баланс не изменится, но появится запись в истории).

## 4. План миграции на Flask

| Шаг | Что делаем | Риск |
|---|---|---|
| **1. Ядро** | `models.py` оставить; `session` заменить на фабрику сессий (на запрос), чтобы не было общего состояния | низкий |
| **2. Пароли** | добавить хэширование (например, `werkzeug.security`), мигрировать существующих пользователей | средний: старые пароли в открытом виде |
| **3. Роли** | регистрация только клиента; менеджер/админ — через `seed` или администратора | низкий |
| **4. Владелец** | во все операции добавить `current_user.id` и проверку принадлежности счёта | низкий, но легко забыть место |
| **5. Маршруты** | `ui/*_frame.py` → страницы: `/login`, `/register`, `/accounts`, `/transfer`, `/salary`, `/history`, `/manager/*`, `/admin/*` | средний: много форм |
| **6. Шаблоны** | Jinja: базовый шаблон + страницы по ролям | низкий |
| **7. Command** | переписать отмену на классы действий | средний |
| **8. Тесты** | юнит (сервисы с моками), интеграционные (БД), сценарные (жизненный цикл заявки) | низкий, но объёмный |

**Что можно не переписывать:** модели, репозитории (кроме `BankRepository`), `BankService`/`ManagerService` — они уже отделены от интерфейса. Это и есть польза слоистой архитектуры: меняется только слой представления.

## 5. Что делать в первую очередь

1. **D-2 и D-3** — без них веб-версия будет небезопасной, а ВПО ЛР4 нечего проверять.
2. **D-1** — хэширование паролей, иначе первый же дефект в `ISSUES.md` останется открытым.
3. **D-6** — сессия вместо статического поля: это условие, без которого Flask просто не заработает правильно.

## 6. Что это даёт ВПО

- **ЛР1 п.3**: дефекты D-1…D-9 готовы к переносу в `ISSUES.md` — с файлом, строкой и ожидаемым поведением.
- **ЛР1 п.4**: жизненный цикл заявки уже есть в коде (`pending → approved/rejected`), диаграмма ляжет на реальные переходы.
- **ЛР4 п.3**: IDOR (D-3) — готовый сценарий проверки безопасности.
- **ЛР2**: D-8 закрывается тестами, а сервисы уже отделены от интерфейса — их удобно тестировать.
