# Статическая проверка кода линтером (ЛР5 п. 4)

Инструмент: **ruff 0.17.3**. Настройки — в `pyproject.toml` (`[tool.ruff]`, `[tool.ruff.lint]`).

## 1. Что показал первый прогон

| Профиль правил | Найдено | Комментарий |
|---|---|---|
| `ruff check` с набором проекта до ЛР5 (E, F, W, I, B, UP, C4, SIM) | 0 | базовые ошибки отсутствовали |
| `ruff check --select ALL` | **1775** | по категориям: 426 ANN001, 333 ANN201, 264 D103, 188 D102, 115 PLR2004, 71 RUF001… |
| расширенный рабочий набор (E, F, W, I, N, B, UP, C4, SIM, S, PT, RUF, PL, RET, COM, ARG) | **67** | реальные замечания, которые стоит разобрать |

`--select ALL` в этом проекте не годится как критерий: он требует docstring и аннотаций типов
у каждой функции (ANN, D), копирайт-заголовка в каждом файле (CPY001) и запрещает кириллицу
в строках (RUF001…003) — для русскоязычного учебного проекта это шум, а не дефекты.

## 3. Что оставлено под ignore и почему

| Правило | Причина |
|---|---|
| `E501` (длина строки) | переносы делаются по смыслу, а не по счётчику; в шаблонах и документации длинные строки неизбежны |
| `RUF001`, `RUF002`, `RUF003` | проект русскоязычный: «с», «о», «а» в тексте — кириллица, а не опечатка |
| `PLR2004` | «магические числа» вида `0.001` (допуск сравнения денег) читаются лучше константы |
| `PLR0911`, `PLR0912`, `PLR0913`, `PLR0915`, `PLR0917` | сервисы намеренно написаны «плоским» набором guard-ветвей: это читаемее и легче тестируется, чем вложенные условия |
| `S608` | SQL в `db_migrate.py` собирается из фиксированных имён таблиц и колонок, пользовательский ввод туда не попадает |
| `S105` | `SECRET_KEY` по умолчанию — только для локального запуска; в бою задаётся переменной окружения |

**Про исключения для тестов и скриптов** (`tests/*`, `tools/*`, `load/*`): в тестах пароли
и временные файлы — часть данных (S105–S108), а `assert` — рабочий инструмент (S101).
Скрипты отчётности пишут файлы и печатают в консоль (S108, T201) — это их работа.

## 4. Результат

```bash
$ ruff check .
All checks passed!
```

Линтер встроен в рабочий цикл: перед каждым блоком и после него `ruff check .` должен быть
чистым. Что линтер **не** находит: нарушения бизнес-логики (например, ISSUE-11 — отрицательный
баланс при отмене) и дыры в правах доступа (ISSUE-3, ISSUE-15) — их нашли тесты и проверки
безопасности, а не статический анализ.
