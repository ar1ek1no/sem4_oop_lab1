# План нагрузочного тестирования (ЛР5 п. 1)

## 1. Цель

Проверить, выполняются ли нефункциональные требования по производительности, и найти
предел системы:

| Требование | Что проверяем |
|---|---|
| **NFR-1** | время ответа на действие пользователя ≤ 1 с на локальных данных |
| **NFR-6** | при 20 одновременных пользователях (паузы 1–3 с): доля ошибок ≤ 1 %, p95 ≤ 1 с, пропускная способность ≥ 10 запросов/с |
| — | точка деградации: при каком числе пользователей p95 превышает 1 с или ошибки превышают 1 % |
| — | гипотеза об узком месте: какой ресурс исчерпывается первым |

## 2. Объект и окружение

| Компонент | Значение |
|---|---|
| Приложение | версия 0.2.0, Flask 3 + SQLite, `flask run` (dev-сервер, один процесс, threaded) |
| Хост | WSL2, Ubuntu 26.04, Python 3.14.4, 8 vCPU |
| Генератор | Locust 2.47, **на той же машине**, что и приложение |
| База | SQLite-файл во `/tmp`, 6 банков, 6 предприятий, 5 пользователей, счета клиента |
| Инструмент | `load/locustfile.py` |

**Ограничение достоверности (важно для защиты):** генератор нагрузки и приложение работают на
одной машине и делят CPU. Абсолютные значения занижены, а точка деградации наступает раньше,
чем на отдельном сервере. Для честных цифр нужен отдельный генератор — это указано в выводах.

## 3. Профиль нагрузки

Сценарий повторяет сессию клиента и менеджера из вариантов использования:

| Действие | Вес | Запросы |
|---|---|---|
| Просмотр своих счетов | 6 | `GET /api/v1/accounts` |
| История операций | 4 | `GET /api/v1/history?limit=20` |
| Справочник банков | 2 | `GET /api/v1/banks` |
| Небольшой перевод (запись в БД) | 1 | `POST /api/v1/transfer` (0.01 BYN) |
| Менеджер: регистрации, заявки, счета, история | 1 (класс) | `GET /api/v1/manager/*` |

- пауза между запросами пользователя: **1–3 с** (клиент), **2–4 с** (менеджер);
- вход выполняется один раз в `on_start` и не участвует в постоянной нагрузке;
- соотношение клиентов и менеджеров — 4 : 1;
- длительность одной точки: 20 с, ramp — все пользователи стартуют сразу (`-r = -u`).

## 4. Виды прогонов

| Прогон | Пользователи | Цель |
|---|---|---|
| Базовый | 1 | эталон времени ответа и пропускной способности без конкуренции |
| Нагрузочный | 20 (целевое из NFR-6) | проверка требования |
| Стрессовый | 30, 50, 80, 120, 200, 400 | поиск точки деградации и отказа |

Команда точки:

```bash
locust -f load/locustfile.py --headless -u 20 -r 20 -t 20s \
       --host http://127.0.0.1:5005 --csv docs/load/u20
```

## 5. Метрики и критерии

| Метрика | Формула / способ | Критерий |
|---|---|---|
| Пропускная способность | `RPS = requests / duration` (Locust) | ≥ 10 запросов/с при 20 пользователях |
| Время ответа | p50, p95, p99 из отчёта Locust | p95 ≤ 1 с |
| Доля ошибок | `errors / requests · 100 %` | ≤ 1 % |
| Точка деградации | первое число пользователей, где p95 > 1 с или ошибки > 1 % | фиксируем и объясняем |
| Устойчивость | рост p95 между соседними точками | не более чем в 3 раза до деградации |

## 6. Что делаем с результатом

1. Строим график «время отклика и RPS от числа пользователей».
2. Определяем точку деградации и точку отказа.
3. Выдвигаем гипотезу об узком месте и проверяем её косвенно: профиль запросов, логи,
   поведение при чтении и при записи.
4. Предлагаем меры: индексы, пул соединений, WSGI-сервер, кэш, отдельная БД.

## 7. Артефакты

- `load/locustfile.py` — профиль нагрузки;
- `load/u{N}_stats.csv` — сырые отчёты Locust по точкам;
- [`LOAD_RESULTS.md`](LOAD_RESULTS.md) — результаты, график, точка деградации, узкое место;
- `load/response-time.png` — график.
