# Спецификация требований: «Управление финансовой системой»

Документ для ЛР1 п. 2 и п. 3. База — приложение `oop_lab1_sem4` (клиент / менеджер / администратор).

**Номера требований не меняются:** на них ссылаются тест-кейсы (ЛР3) и матрица трассируемости (ЛР5). Новые требования только добавляются в конец с новыми номерами.

Связанные документы: [`STATE_DIAGRAM.md`](STATE_DIAGRAM.md) — жизненный цикл заявки и счёта; [`../ISSUES.md`](ISSUES.md) — дефекты, найденные при сверке требований с приложением.

## 1. Бизнес-требования

| ID | Требование | Источник |
|---|---|---|
| **BR-1** | Дать частному клиенту возможность открывать счета и вклады в разных банках и переводить между ними средства без посещения отделения | боль клиента: несколько приложений банков |
| **BR-2** | Дать предприятию возможность платить сотрудникам зарплату через платформу, а не разовыми переводами | боль предприятия: ручные ведомости |
| **BR-3** | Обеспечить контроль: регистрация клиентов и зарплатные проекты подтверждаются менеджером; все действия фиксируются, ошибочные можно отменить | требование банка к подотчётности |
| **BR-4** | Обеспечить прозрачность: клиент видит историю движений своих средств, менеджер — историю своих клиентов, администратор — все действия | доверие пользователя |

## 2. Пользовательские требования (use case)

**UC-1. Регистрация с подтверждением.**
Акторы: клиент, менеджер. Клиент регистрируется (логин, пароль, ФИО). Учётная запись создаётся неподтверждённой и не даёт войти. Менеджер видит список ожидающих, подтверждает или отклоняет. После подтверждения клиент входит.
Способ проверки: позитивный сценарий подтверждения и негативный — вход до подтверждения.

**UC-2. Открытие счёта и перевод.**
Актор: клиент. Клиент открывает счёт в выбранном банке, затем переводит средства на другой свой счёт или вклад. Система проверяет владельца счёта, блокировку и достаточность средств, списывает и зачисляет, пишет историю.
Способ проверки: перевод между своими счетами; попытка перевода с чужого счёта (IDOR); попытка при недостатке средств.

**UC-3. Вклад и начисление.**
Актор: клиент. Клиент создаёт вклад, переводит на него средства, запускает начисление процента. Процент начисляется только на вклады, а не на обычные счета. Закрытие вклада возвращает средства на счёт.
Способ проверки: начисление увеличивает баланс вклада и не меняет баланс счёта.

**UC-4. Зарплатный проект.**
Акторы: клиент, менеджер. Клиент видит предприятия и подаёт заявку на зарплатный проект. Менеджер подтверждает или отклоняет. После подтверждения клиент получает зарплату на любой свой незаблокированный счёт — один раз за расчётный период.
Способ проверки: получение до подтверждения — отказ; после — зачисление; повторное получение в том же периоде — отказ.

**UC-5. Блокировка и отмена действий.**
Акторы: менеджер, администратор. Менеджер блокирует счёт — переводы с него запрещены. Администратор видит журнал всех действий и отменяет ошибочную операцию; отмена возвращает прежнее состояние и сама попадает в журнал.
Способ проверки: перевод с заблокированного счёта — отказ; отмена перевода возвращает оба баланса.

## 3. Функциональные требования

| ID | Требование | Приоритет | Способ проверки |
|---|---|---|---|
| **FR-1** | Пользователь регистрируется, указав логин, пароль и ФИО | высокий | позитивный сценарий; негативные: пустой логин, короткий пароль, занятый логин, пустое ФИО |
| **FR-2** | Новая учётная запись создаётся неподтверждённой и не даёт войти | высокий | вход до подтверждения → отказ с понятным сообщением |
| **FR-3** | Менеджер видит список неподтверждённых и может подтвердить **или отклонить** | высокий | подтвердить → вход работает; отклонить → вход запрещён |
| **FR-4** | Пользователь входит по логину и паролю и получает роль | высокий | вход каждой из трёх ролей → доступны только свои функции |
| **FR-5** | Клиент видит список всех банков системы | средний | список непуст и совпадает с таблицей `banks` |
| **FR-6** | Клиент открывает счёт или вклад в выбранном банке | высокий | счёт появляется в списке и в БД с нулевым балансом и правильным типом |
| **FR-7** | Клиент закрывает свой счёт; закрыть можно только при нулевом балансе и без блокировки | высокий | попытка закрыть счёт с остатком → отказ; чужой счёт → отказ |
| **FR-8** | Клиент переводит средства между своими счетами и вкладами | высокий | баланс списан и зачислен, в истории одна запись |
| **FR-9** | Перевод невозможен при недостатке средств | высокий | сумма больше баланса → отказ, балансы не меняются |
| **FR-10** | История движений показывает откуда, куда, сколько и когда | высокий | после перевода в истории запись с корректными полями |
| **FR-11** | Клиент создаёт вклад и запускает начисление процента; начисление касается только вкладов | средний | баланс вклада вырос на 5 %, баланс счёта не изменился |
| **FR-12** | Клиент видит доступные предприятия и подаёт заявку на зарплатный проект | средний | заявка создаётся в статусе «ожидает»; повторная заявка → отказ |
| **FR-13** | После подтверждения заявки клиент получает зарплату на свой незаблокированный счёт, не чаще одного раза за период | средний | до подтверждения → отказ; после → зачисление; повторно → отказ |
| **FR-14** | Менеджер блокирует и разблокирует счёт; с заблокированного перевод невозможен | высокий | перевод с заблокированного → отказ с сообщением |
| **FR-15** | Администратор видит журнал всех действий и может отменить действие | высокий | отмена возвращает состояние (баланс, статус) и пишет новую запись |
| **FR-16** | JSON API `/api/v1` повторяет ключевые операции (вход по токену, счета, перевод, история) | средний | Postman: позитивные и негативные запросы, коды 200/400/401/403/404 |

## 4. Нефункциональные требования

| ID | Требование | Критерий проверки |
|---|---|---|
| **NFR-1** | Отклик интерфейса на действие пользователя — не более 1 с на локальных данных | замер времени ответа на 20 операциях |
| **NFR-2** | Пароли не хранятся в открытом виде | в БД нет читаемого пароля; вход работает |
| **NFR-3** | Ошибки не раскрывают внутренние детали (стек, пути, SQL) | спровоцировать ошибку (неверный ввод, недоступная БД) → сообщение без технических подробностей |
| **NFR-4** | Все значимые действия логируются | журнал в БД содержит запись для каждого действия из FR-6…FR-15; файл `logs/app.log` содержит те же события |
| **NFR-5** | Клиент не может получить доступ к чужим данным, подменив идентификатор | подмена `id` в адресе и в запросе → отказ 403/404 |
| **NFR-6** | При 20 одновременных пользователях с паузами между действиями 1–3 с: доля ошибок ≤ 1 %, p95 времени ответа ≤ 1 с, пропускная способность ≥ 10 запросов/с | прогон в Locust по профилю нагрузки (ЛР5) |

## 5. Жизненный цикл сущности

Заявка на зарплатный проект: `ожидает решения → подтверждена → выплата проведена`, ветка отказа и отзыв подтверждения. Второй кандидат — счёт: `открыт → заблокирован → открыт`, `открыт → закрыт` (конечное). Переходы, события и условия — в [`STATE_DIAGRAM.md`](STATE_DIAGRAM.md).
