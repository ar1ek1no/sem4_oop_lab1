# Отчёты о дефектах (ЛР3 п. 5)

Полный реестр — [`../ISSUES.md`](../requirements/ISSUES.md) (18 записей). Здесь — подробные отчёты по дефектам, найденным при верификации требований (ЛР1) и при выполнении тест-кейсов (ЛР3): по одному из каждой категории важности и все, что меняли поведение предметной области.

Поля отчёта: краткое описание, подробное (ожидаемый и фактический результат, требование), шаги воспроизведения, воспроизводимость, важность и срочность, симптом, возможность обойти, статус.

## DR-1. Пароли хранятся в открытом виде (ISSUE-1)

**Краткое:** пароль сохраняется в БД и сравнивается без хэширования.
**Подробное.** Ожидаемый результат: в БД необратимый хэш, сравнение по хэшу (NFR-2). Фактический: `models.py` — `password = Column(String)`, `auth_service` сравнивал строки. В таблице `users` лежали читаемые пароли `123`.
**Шаги:** 1) открыть `finance.db`; 2) `SELECT username, password FROM users;`; 3) войти под любым пользователем, зная пароль из таблицы.
**Воспроизводимость:** 100 %.
**Важность:** критический. **Срочность:** высокий.
**Симптом:** утечка файла БД = утечка всех паролей.
**Обход:** нет.
**Статус:** исправлен. Хэш `werkzeug.security`, миграция перевела 7 старых паролей, колонка `password` удалена. Проверка: `test_migration.py::test_plain_password_removed`, `test_auth_service.py::test_authenticate_ok`.

## DR-2. Регистрация позволяет выбрать роль администратора (ISSUE-2)

**Краткое:** публичная регистрация создаёт пользователя с любой ролью из формы.
**Подробное.** Ожидаемый результат: регистрируется только клиент, остальные роли создаёт администратор/`seed` (FR-1, FR-4). Фактический: `register(username, password, role)`, форма передавала выбранную роль; проверки роли не было.
**Шаги:** 1) открыть регистрацию; 2) выбрать `admin`; 3) зарегистрироваться; 4) войти.
**Воспроизводимость:** 100 %.
**Важность:** критический. **Срочность:** немедленно.
**Симптом:** любой получает доступ к журналу и отмене операций.
**Обход:** нет.
**Статус:** исправлен. `AuthService.register` не принимает роль, всегда `client`. Проверка: `test_auth_web.py::test_register_ignores_role_from_form`.

## DR-3. Перевод с чужого счёта по подмене id (ISSUE-3)

**Краткое:** зная `id`, клиент переводит деньги с чужого счёта.
**Подробное.** Ожидаемый результат: списание только со своего счёта, чужой `id` — отказ (NFR-5, FR-8). Фактический: `transfer_money(from_id, to_id, amount)` проверял блокировку и баланс, но не владельца.
**Шаги:** 1) войти клиентом A; 2) отправить перевод с `from_id` счёта клиента B; 3) проверить баланс B.
**Воспроизводимость:** 100 %.
**Важность:** критический. **Срочность:** немедленно.
**Симптом:** кража средств через подмену идентификатора.
**Обход:** нет.
**Статус:** исправлен. `AccountRepository.get_for_user(from_id, user_id)` в каждой операции; чужой счёт неотличим от несуществующего. Проверка: `test_client_web.py::test_transfer_from_foreign_account`, `test_api.py::test_account_detail_idor`.

## DR-4. Закрытие чужого счёта (ISSUE-15)

**Краткое:** зная `id` чужого счёта с нулевым балансом, можно его удалить.
**Подробное.** Ожидаемый результат: закрывать можно только свои счета (NFR-5, FR-7). Фактический: `close_account(acc_id)` не принимал `user_id` и не проверял принадлежность.
**Шаги:** 1) войти клиентом A; 2) отправить закрытие счёта клиента B; 3) счёт исчезает.
**Воспроизводимость:** 100 %.
**Важность:** критический. **Срочность:** немедленно.
**Симптом:** удаление чужих счетов, потеря истории.
**Обход:** нет.
**Статус:** исправлен. Закрытие через `get_for_user`, счёт не удаляется физически, а помечается `is_closed`. Проверка: `test_client_web.py::test_close_foreign_account_denied`.

## DR-5. Зарплата без подтверждённой заявки (ISSUE-4)

**Краткое:** выплата проходит, если клиент есть в штате, даже без заявки.
**Подробное.** Ожидаемый результат: только по заявке в статусе `approved` (FR-12, FR-13). Фактический: `get_salary` проверял лишь запись в `employment`, статус заявки не читался.
**Шаги:** 1) менеджер добавляет клиента в штат; 2) клиент получает зарплату, не подавая заявку.
**Воспроизводимость:** 100 % при наличии записи в `employment`.
**Важность:** высокий. **Срочность:** обычный.
**Симптом:** выплаты без одобрения.
**Обход:** нет.
**Статус:** исправлен. `pay_salary` требует `approved` заявку, оклад берётся из `employment.salary_amount`, повторная выплата в том же месяце запрещена. Проверка: `test_salary_lifecycle.py::test_salary_lifecycle`.

## DR-6. Отмена выплаты уводит баланс в минус (ISSUE-11)

**Краткое:** откат зарплаты вычитает сумму без проверки остатка.
**Подробное.** Ожидаемый результат: отмена не создаёт отрицательный баланс, при нехватке средств — отказ (BR-3, FR-15). Фактический: `balance -= amount` без проверки; в рабочей БД счёт имел `-500`.
**Шаги:** 1) получить зарплату 1000; 2) потратить 700; 3) администратор отменяет выплату; 4) баланс −700.
**Воспроизводимость:** 100 % при остатке меньше суммы отмены.
**Важность:** высокий. **Срочность:** высокий.
**Симптом:** отрицательные балансы, которые невозможно объяснить клиенту.
**Обход:** нет.
**Статус:** исправлен. Команда `SalaryCommand` проверяет остаток и возвращает понятный отказ. Проверка: `test_commands.py::TestSalaryCommands::test_salary_not_enough_money`, `test_admin_service.py::test_undo_rejected_by_command`.

**Обход:** нет.
