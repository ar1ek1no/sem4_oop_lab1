## Пять лаб: что именно нужно

### Лаба 1. README и требования

- **README.md**: название, назначение, целевые пользователи; стек (язык, фреймворки, СУБД); архитектура и схема компонентов; перечень модулей с ответственностью; точки интеграции (БД, файловая система, внешние сервисы); инструкция запуска.
- **Спецификация требований** (`/docs`): бизнес-требования (назначение, проблема, цели); **≥5 пользовательских требований** с use case; **≥15 функциональных**; **≥5 нефункциональных**.
- **Верификация требований**: для каждого требования — способ проверки; требования без способа проверки переписать; расхождения с приложением — в `ISSUES.md`.
- **Диаграмма состояний** сущности с жизненным циклом: начальное и конечное состояния, события и условия на переходах.

### Лаба 2. Тесты

- Юнит-тесты, интеграционные (с БД), сценарные (переходы состояний из лабы 1).
- Требования: Arrange–Act–Assert; понятные названия; параметризованные тесты; негативные (исключения, неверный ввод, границы); независимость тестов; моки в юнит-тестах; заглушки HTTP в интеграционных.
- **Покрытие ≥ 70 %** (pytest-cov или аналог); не считаются миграции, конфигурации, сгенерированный код.

### Лаба 3. План тестирования и тест-кейсы

- **План тестирования**: цель; области, подвергаемые и не подвергаемые тестированию (со ссылками на FR/NFR и обоснованием); тестовая стратегия (уровни: модульное, интеграционное, сценарное, системное ручное, UI, API, нагрузочное; виды; инструменты); критерии (приёмочные, начала, приостановки, возобновления, завершения) через метрики; метрики — % успешного прохождения, % выполнения, покрытие требований тест-кейсами, % устранения дефектов по важности (формулы — раздел 6.2 методички).
- **Чек-лист** по всем функциональным требованиям, сгруппированный по модулям; для каждого — позитивные и негативные проверки.
- **≥25 тест-кейсов** с атрибутами: id, приоритет, требование, модуль, заглавие, исходные данные, шаги, ожидаемый результат. Покрыть все FR высокого приоритета.
- **Выполнение** кейсов: результат, статус, скриншоты.
- **Отчёты о дефектах**: краткое и подробное описание (ожидаемый/фактический результат, ссылка на требование), шаги воспроизведения, воспроизводимость, важность и срочность, симптом, возможность обойти.

### Лаба 4. Вёрстка, API, безопасность, UI-автотесты

- **Вёрстка и совместимость**: целостность блоков, сетка, обтекание; адаптивность (ширина, масштаб); интерактив (кликабельность, фокус, наведение, логотип, favicon); реальные данные (длинные и короткие строки, пустые списки, много элементов); отсутствие 404 и ошибок в консоли (DevTools: Network, Console); **≥3 браузера** + мобильная эмуляция; таблица «проверка × браузер».
- **Postman**: коллекция на все эндпоинты вариантов использования — позитивные (код, структура, значения), негативные (без авторизации, неверные данные, несуществующие ручки), связывание запросов (токен из логина), запуск с отчётом.
- **Безопасность**: доступ в закрытую зону по прямому URL; подмена идентификатора (IDOR); сообщения об ошибках без стека, путей и SQL; логирование операций и ошибок.
- **UI-автотесты** (Selenium или Playwright): Page Object; каждый тест создаёт свои данные; явные ожидания вместо пауз; скриншот при падении.

### Лаба 5. Нагрузка, линтер, трассируемость

- **План нагрузочного тестирования**: цели из NFR; профиль нагрузки (действия, число пользователей, паузы); виды — нагрузочный и стрессовый; критерии успешности (доля ошибок, время ответа).
- **Прогоны**: базовый (1 пользователь), нагрузочный (целевое число), стрессовый (до деградации); результаты, пропускная способность, доля ошибок; график времени отклика от числа пользователей; **точка деградации**; гипотеза об узком месте.
- **Линтер**: статическая проверка, разбор и исправление нарушений.
- **Матрица трассируемости**: требования ↔ работы; покрытие требований тест-кейсами; требования без тестов; тесты без требований; требования с наибольшим числом дефектов.

## Что нужно технически

Для лаб 4–5 нужны веб-интерфейс и HTTP, поэтому слой представления переводится на **Flask + Jinja**; доменная логика и модели остаются. По ходу закрываются дефекты из `ISSUES.md` — они же идут в отчёты о дефектах.

## Как работаем

- **Код пишешь ты**, в файлы проекта. Заданий «сделай сама» не давай.
- Блок начинается с 3–5 фраз «что делаем и зачем», потом код, потом 3–5 вопросов по-русски.
- Короткие пункты, читаю с ноутбука.
- Каждый блок заканчивается записью в `BLOCKS.md` (что и где изменено).
