## 1. Что это за проект — на пальцах

Есть банковское веб-приложение «Управление финансовой системой». В нём три роли:

- **клиент** — регистрируется, открывает счета и вклады, переводит деньги, подаёт заявку
  на зарплатный проект и получает зарплату, смотрит историю;
- **менеджер** — подтверждает или отклоняет регистрации и заявки, блокирует счета, смотрит штат
  предприятий и историю клиента;
- **администратор** — видит журнал всех действий и может отменить ошибочную операцию.

Приложение сделано на **Flask + SQLite**, данные — в файле `finance.db`, вход по логину и паролю,
у каждого своя роль. Это не «игрушка на один экран»: есть HTTP-API (`/api/v1/...`), по которому
можно дергать систему из Postman и нагружать её Locust.

**Почему это важно для ВПО:** предмет про *проверку* программ. Проверять нужно что-то работающее.
Поэтому один проект используется пять раз: сначала к нему пишут требования (ЛР1), потом его
тестируют (ЛР2), потом оформляют процесс тестирования (ЛР3), потом проверяют вёрстку, API
и безопасность (ЛР4), потом — производительность и трассируемость (ЛР5).

## 2. Минимальный словарь (без него дальше будет тяжело)

| Слово | Простыми словами |
|---|---|
| **Требование** | Условие, которому должна соответствовать программа. «Клиент может перевести деньги» — требование. |
| **FR (функциональное)** | *Что* система делает: вход, перевод, закрытие счёта. |
| **NFR (нефункциональное)** | *Как* она это делает: быстро, безопасно, с логами. |
| **Use case** | Сценарий: кто (актор) и что делает по шагам. |
| **Дефект (баг)** | Расхождение между тем, что должно быть, и тем, что есть. |
| **Важность / срочность** | Насколько вреден дефект / как быстро его чинить. Это разные вещи. |
| **Тест-кейс** | Подробный сценарий проверки: данные, шаги, ожидаемый результат. |
| **Чек-лист** | Список «что проверить» без шагов. Кейс подробнее чек-листа. |
| **Позитивный / негативный тест** | Проверяем, что всё работает / проверяем, что система правильно отказывает. |
| **Мок** | «Заглушка» вместо настоящего объекта: возвращает заранее заданный ответ. |
| **Покрытие (coverage)** | Какая доля кода или требований проверена тестами. |
| **Регрессия** | Проверка, что старое не сломалось после изменений. |
| **IDOR** | Подмена `id` в запросе, чтобы получить чужой объект (чужой счёт). |
| **Токен** | Строка, которую сервер выдал после входа; её подставляют в следующие запросы. |
| **Page Object** | Класс страницы: локаторы и действия в одном месте, тест вызывает методы. |
| **p95** | 95 % запросов быстрее этого времени. Показывает «плохой» опыт, в отличие от среднего. |
| **Точка деградации** | Нагрузка, при которой время ответа выходит за допустимое. |
| **Линтер** | Инструмент статической проверки кода (у нас `ruff`). |
| **Трассируемость** | Таблица связей: требование → где реализовано → какие тесты → какие дефекты. |
| **CI/CD** | Автоматическая сборка/проверка/доставка кода. Спрашивают на любой лабе. |

## 3. Как устроен проект (одна картинка в голове)

Слои идут сверху вниз, каждый знает только про соседа:

```
браузер / Postman / Locust
        ↓ HTTP
веб-слой: web/*.py (маршруты) + templates/ (Jinja) + static/ (CSS, JS)
        ↓ вызов
сервисы: services/*.py — бизнес-правила (нельзя перевести больше, чем есть)
        ↓
репозитории: repositories/*.py — запросы к базе
        ↓
модели и база: models.py + finance.db (SQLite)
```

Зачем так: тестировщику можно проверять сервисы без браузера (юнит-тесты), а браузерные тесты
не знают про SQL. Если поменять цвет кнопки — сервисы не трогаем, тесты логики не падают.

Ключевые файлы:

| Файл | Что внутри |
|---|---|
| [`app.py`](app.py) | собирает приложение, обрабатывает ошибки 400/403/404/500 |
| [`models.py`](models.py) | 7 таблиц: пользователи, банки, предприятия, счета, журнал, заявки |
| [`services/`](services/) | правила: вход, переводы, зарплата, отмена |
| [`web/`](web/) | страницы и JSON API |
| [`templates/`](templates/) | HTML-шаблоны |
| [`tests/`](tests/) | 267 автотестов + 15 браузерных |
| [`docs/`](docs/README.md) | документы по лабораторным (см. индекс) |

Как запустить:

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
python seed.py                  # демо-данные
flask --app app run --debug     # http://127.0.0.1:5000
```

Учётки: `client1 / client1`, `manager1 / manager1`, `admin1 / admin1`.

## 4. Лабораторные по порядку

### ЛР1. Требования, README, дефекты, диаграмма состояний

**Условие из задания:** описать проект в `README.md` (название, назначение, пользователи, стек,
архитектура, модули, точки интеграции, запуск); написать спецификацию в `docs` (бизнес-требования,
≥ 5 use case, ≥ 15 FR, ≥ 5 NFR и способ проверки каждого); сверить требования с приложением,
расхождения — в `ISSUES.md`; нарисовать диаграмму состояний сущности с жизненным циклом.

**Что хотят на самом деле:** чтобы ты понимала, что такое требование, умела отличить FR от NFR,
показала, как требования проверяются, и не врала, что «всё идеально» — дефекты должны быть.

**Что сделано и где смотреть:**

| Артефакт | Файл | Что сказать |
|---|---|---|
| Описание проекта | [`README.md`](README.md) | «Стек — Flask и SQLite, три роли, слоистая архитектура, запуск одной командой» |
| Требования | [`docs/lab1/SRS_finance.md`](docs/lab1/SRS_finance.md) | «4 бизнес-требования, 5 сценариев, 16 FR, 6 NFR, у каждого — способ проверки» |
| Дефекты | [`docs/lab1/ISSUES.md`](docs/lab1/ISSUES.md) | «18 расхождений, 4 критических: пароли, выбор роли, два IDOR» |
| Диаграмма состояний | [`docs/lab1/STATE_DIAGRAM.md`](docs/lab1/STATE_DIAGRAM.md) | «Заявка: ожидает → подтверждена/отклонена → выплата за период» |

Подробный разбор и вопросы: [`docs/lab1/README.md`](docs/lab1/README.md).

**Вопросы, которые задают, и короткий ответ:**

1. *Что такое требование и зачем?* — Условие, которому должна соответствовать система; чтобы
   разработчик и тестировщик понимали результат одинаково.
2. *Уровни требований?* — Бизнес → пользовательские (use case) → функциональные и нефункциональные.
3. *FR и NFR?* — FR: что делает (перевод). NFR: как делает (быстро, безопасно, с логами).
4. *Почему у тебя 16 FR, а не 15?* — Добавили API как отдельное требование, иначе тесты API
   были бы «без требования».
5. *Где начальное и конечное состояние на диаграмме?* — Начальное: заявки нет. Конечное:
   «отклонена». Ветка «подтверждена → выплата» зацикливается на новый период.
6. *Почему повторная выплата не нарисована состоянием?* — Это запрет операции, а не состояние;
   проверяется в сервисе и негативным тестом.

### ЛР2. Тесты и покрытие

**Условие:** написать юнит-тесты (с моками), интеграционные (с БД) и сценарные (переходы состояний
из ЛР1); Arrange–Act–Assert, понятные имена, параметризация, негативные и граничные случаи,
независимость тестов; покрытие ≥ 70 % инструментом.

**Что хотят:** чтобы ты умела писать тесты разных уровней и могла пальцем показать, где мок,
где настоящая БД и почему тесты не зависят от порядка запуска.

**Что сделано:**

- **267 автотестов:** 148 модульных (без БД, с моками), 114 интеграционных (HTTP + SQLite),
  5 сценарных (цепочки переходов состояний).
- **Покрытие 94,69 %** при пороге 70 % — [`docs/lab2/COVERAGE.md`](docs/lab2/COVERAGE.md).
- **Каждый тест получает свою БД во временной папке**, поэтому порядок запуска не важен
  и рабочая `finance.db` не портится.
- **Негативные проверки:** чужой счёт, заблокированный счёт, сумма больше баланса, повторная
  выплата, пустое ФИО, короткий пароль.

Смотреть: [`docs/lab2/README.md`](docs/lab2/README.md), [`tests/`](tests/),
[`tests/unit/test_bank_service.py`](tests/unit/test_bank_service.py),
[`tests/scenario/test_salary_lifecycle.py`](tests/scenario/test_salary_lifecycle.py).

**Вопросы и ответы:**

1. *Модульное vs интеграционное vs системное?* — Один компонент изолированно / стыки компонентов
   и БД / вся система глазами пользователя.
2. *Что такое мок?* — Замена объекта заглушкой с заданным ответом; проверяем логику без БД.
3. *Чёрный/белый/серый ящик?* — По входу-выходу / с доступом к коду / частично.
4. *Почему тесты независимы?* — Своя БД и свои данные на тест; иначе падение одного ломает другие.
5. *Что выявляет интеграционное после модульного?* — Несовпадение форматов, ошибки стыков,
   проблемы транзакций и прав доступа.

**Вопросы и ответы:**

1. *Чек-лист vs тест-кейс?* — Список проверок без шагов / подробный сценарий с данными и ожиданием.
2. *Атрибуты кейса?* — ID, приоритет, требование, модуль, заглавие, данные, шаги, ожидаемый результат.
3. *Важность vs срочность?* — Вред для продукта / скорость исправления. Могут не совпадать.
4. *Формула TSP?* — Успешные / выполненные × 100 %. У нас 52/52 = 100 %.
5. *Зачем критерии приостановки?* — Чтобы не тратить время, если тесты массово падают из-за

6. *Почему кейсов 52, а требований 22?* — На важные требования по несколько кейсов (позитив
   и негатив), плюс проверки безопасности и нефункциональные.

### ЛР4. Вёрстка, API в Postman, безопасность, UI-автотесты

**Условие:** проверить вёрстку и совместимость (адаптивность, интерактив, реальные данные,
консоль, ≥ 3 браузера + мобильная эмуляция, таблица «проверка × браузер»); собрать Postman-коллекцию
на все варианты использования с позитивными и негативными запросами и отчётом; проверить
безопасность (прямой URL, IDOR, ошибки без стека, логирование); написать UI-автотесты
(Playwright/Selenium, Page Object, свои данные, явные ожидания, скриншот при падении).

**Что хотят:** чтобы ты умела смотреть на приложение глазами пользователя и злоумышленника,
а не только «работает — не работает».

**Что сделано:**

- **Кроссбраузерность:** 15 одинаковых проверок в Chromium, Firefox и WebKit — все ✅
  ([`docs/lab4/COMPATIBILITY.md`](docs/lab4/COMPATIBILITY.md)). На мобильной ширине таблицы
  превращаются в карточки, страница не прокручивается горизонтально.
- **Postman:** 37 запросов, 57 проверок, 0 провалов; токен из логина подставляется в следующие
  запросы ([`docs/lab4/API_TESTING.md`](docs/lab4/API_TESTING.md), коллекция в
  [`docs/lab4/postman/`](docs/lab4/postman/), отчёт [`newman-report.json`](docs/lab4/newman-report.json)).
- **Безопасность:** 14 проверок — прямой URL без входа (редирект), IDOR (404), ошибки без стека
  и SQL, логи входов и отказов ([`docs/lab4/SECURITY.md`](docs/lab4/SECURITY.md)).
- **UI-тесты:** 15 тестов на Playwright + Page Object ([`tests/ui/`](tests/ui/)),
  запуск `pytest -m ui`.

**Вопросы и ответы:**

1. *Зачем 3 браузера?* — Разные движки по-разному считают CSS; Safari/WebKit и Firefox ловят
   то, что Chromium прощает.
2. *401 vs 403?* — Не вошёл / вошёл, но прав нет.
3. *400 vs 404?* — Плохие данные / объект не найден.
4. *Что такое IDOR и как закрыт?* — Подмена id; сервис ищет счёт только среди **своих**,
   чужой = «не найден» (404).
5. *Почему ошибки не должны показывать стек?* — Это подсказка атакующему и лишний шум пользователю.
6. *Page Object зачем?* — Локаторы и действия страницы в одном классе; тест читается как сценарий,
   при смене вёрстки правится один файл.
7. *Почему явные ожидания?* — Паузы делают тесты медленными и «мигающими»; ждём событие.

### ЛР5. Нагрузка, линтер, матрица трассируемости

**Условие:** план нагрузочного тестирования (цели из NFR, профиль, виды, критерии); прогоны

месте; статическая проверка линтером с исправлением; матрица трассируемости.

**Что хотят:** чтобы ты умела ответить «сколько пользователей система держит и почему падает»,
знала, что линтер ловит не всё, и могла показать, что ни одно требование не забыто.

**Что сделано:**

- **План:** [`docs/lab5/LOAD_PLAN.md`](docs/lab5/LOAD_PLAN.md) — 10 точек нагрузки, профиль клиента
  и менеджера, паузы 1–3 с, критерии.
- **Результаты:** [`docs/lab5/LOAD_RESULTS.md`](docs/lab5/LOAD_RESULTS.md) + график
  [`load/response-time.png`](docs/lab5/load/response-time.png).
  - 20 пользователей: p95 **340 мс**, ошибок 0 %, **11,5 RPS** → NFR-6 выполняется;
  - деградация с **80 пользователей** (p95 > 1 с);
  - при 400 пользователях ошибок всё ещё 0 %, но p95 8,3 с, RPS на плато ~72 — упёрлись
    в один процесс и запись в SQLite.
- **Линтер:** [`docs/lab5/LINTING.md`](docs/lab5/LINTING.md) — расширили правила, исправили
  нарушения, остальное обоснованно исключили; `ruff check .` чистый.
- **Матрица:** [`docs/lab5/TRACEABILITY.md`](docs/lab5/TRACEABILITY.md) — 22 требования, у каждого
  реализация, кейсы, автотесты и дефекты; зоны риска — регистрация и права доступа.

**Вопросы и ответы:**

1. *Нагрузочное vs стрессовое?* — Держит ли целевую нагрузку / где начинается деградация и отказ.
2. *Почему p95, а не среднее?* — Среднее прячет медленные запросы; p95 показывает, что чувствуют люди.
3. *Точка деградации и узкое место?* — Где p95 вышел за порог / какой ресурс исчерпался первым.
4. *Почему генератор и приложение на одной машине — плохо?* — Делят процессор, цифры занижены.
5. *Что линтер не находит?* — Ошибки логики: отрицательный баланс при отмене нашли тесты.
6. *Покрытие требований vs кода?* — «На каждое требование есть кейс» / «какая доля строк исполнена».
7. *Требования без тестов и тесты без требований?* — Первых нет; вторые только технические
   (миграция, репозитории).
8. *Почему зоны с дефектами — зоны риска?* — Там уже были ошибки, выше шанс новых.

## 6. Если спросят про CI/CD (могут на любой лабе)

- **Что решает CI:** автоматически собирает и проверяет каждый коммит, ловит поломку сразу.
- **Delivery vs deployment:** delivery — всегда готово к выкладке (кнопку нажимает человек),
  deployment — выкатывается автоматически.
- **Стадии конвейера:** установка зависимостей → линтер → юнит-тесты → интеграционные →
  сборка → отчёты → (позже) деплой.
- **Какие тесты где:** быстрые (линтер, юнит) на каждый коммит; интеграционные — на каждый коммит
  или PR; UI и нагрузочные — по расписанию/перед релизом, потому что долгие.
- **Quality gate:** набор условий, без которых сборка не проходит (например, покрытие ≥ 70 %,
  нет падений, линтер чист).
- **Flaky-тесты:** нестабильные; их чинят или убирают из конвейера, иначе доверие к CI падает.
- **Зачем отчёты в конвейере:** чтобы по логам сразу видеть, что именно сломалось и на каком тесте.

## 8. Что честно сказать, если спросят «а это всё точно работает?»

- Покрытие кода 94,69 %, а не 100 %: непокрытые строки — редкие ветки обработки ошибок.
- Точка отказа не найдена: при 400 пользователях ошибок нет, только растёт время ответа.
  Это ограничение одного процесса, а не «система идеальна».
- Нагрузка гонялась на dev-сервере Flask и на той же машине, где работал генератор, — цифры
  занижены, для честных нужен отдельный генератор и WSGI-сервер.
- Внешних сервисов в проекте нет, поэтому «заглушек HTTP для внешних сервисов» в тестах нет —
  вместо них моки репозиториев и реальная SQLite.

Такая прямота обычно работает лучше, чем «всё идеально»: видно, что ты понимаешь ограничения.
