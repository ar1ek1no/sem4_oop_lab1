## Что требует задание (коротко)

1. **Тесты трёх видов:** юнит-тесты, интеграционные (взаимодействие с БД), сценарные
   (переходы состояний из ЛР1).
2. **Требования к тестам:** Arrange–Act–Assert, понятные имена, параметризация, негативные
   проверки (исключения, неверный ввод, границы), независимость друг от друга, **моки** в юнит-тестах.
3. **Покрытие ≥ 70 %**, измеренное инструментом (`pytest-cov`).

## Что и как сделано

- **Пирамида:** 148 модульных → 114 интеграционных → 5 сценарных. Модульные быстрые и без БД,
  интеграционные проверяют весь путь запроса, сценарные — только переходы состояний.
- **Моки** подменяют репозитории: юнит-тест проверяет решение сервиса, а не SQL.
  Пример: `tests/unit/test_bank_service.py` — «перевод с чужого счёта → отказ».
- **Независимость:** каждый тест получает своё приложение и свой файл SQLite во временной папке,
  поэтому порядок запуска не важен и тесты не портят рабочую `finance.db`.
- **Негативные и граничные:** пустой логин, пароль из 5 символов, сумма 0, 0.01, миллион + 1,
  чужой счёт, заблокированный счёт, повторная выплата.
- **Покрытие** считается по коду приложения: 94,69 % (порог 70 %).

## Как показывать (7 минут)

1. `pytest` — весь набор зелёный (267 тестов, ~1 минута).
2. `pytest --cov --cov-report=term-missing` — покрытие 94,69 %.
3. Открыть `tests/unit/test_bank_service.py`: «вот мок репозитория и проверка отказа».
4. Открыть `tests/scenario/test_salary_lifecycle.py`: «вот цепочка: подали заявку → подтвердили →
   выплатили → повторно нельзя → отменили → снова можно».

## Вопросы и короткие ответы

**Модульное, интеграционное, системное?** Модульное — один компонент изолированно; интеграционное —
стыки компонентов и БД; системное — вся система глазами пользователя.

**Что такое мок и зачем?** Замена реального объекта «пустышкой» с нужными ответами. Нужен,
чтобы проверять логику без БД и без внешних сервисов.

**Чёрный/белый/серый ящик?** Чёрный — только вход и выход, без кода; белый — с доступом к коду;
серый — частично (например, тесты API + чтение логов).

**Пирамида тестирования?** Много быстрых модульных, меньше интеграционных, ещё меньше системных:
чем выше уровень, тем дороже тест.

**Чем сценарный тест отличается от интеграционного?** Сценарный проверяет последовательность
переходов состояний (бизнес-процесс), интеграционный — взаимодействие компонентов.

**Зачем параметризация?** Один тест проверяет набор значений (границы и классы) без копипасты.

**Почему тест не должен зависеть от порядка?** Иначе падение одного теста «заражает» другие
и результат прогона становится случайным.

**Почему тест на найденный дефект остаётся?** Это регрессионная защита: дефект не вернётся незамеченным.
